# work-report

Пользователь не видит вывод инструментов и не читает дифф. Отчёт - единственное, по чему он судит о результате этапа. Пиши его сам (оркестратор), не делегируй: он держится на контексте всей работы.

## Когда делать (CLAUDE.md, «Экономия лимитов»)

| Ситуация | Что делать |
|---|---|
| Закончен этап из `Docs/GDD.md` (раздел «Порядок реализации») | **Отчёт-страница по этому скиллу** - один на этап, сводит все задачи этапа. Затем коммит и подсказка пользователю, что можно начать новую сессию (`/clear`) |
| Пользователь прямо попросил отчёт | Отчёт-страница |
| Промежуточная задача внутри этапа, правка, настройка, ответ на вопрос | **Отчёт НЕ делать.** Короткий итог в консоли: что сделано, чем проверено (цифры verify), что нужно от пользователя, что дальше. Несколько строк, без страницы и без файла в `Reports/` |
| Остановка на блокере | Короткий итог в консоли с точным вопросом; страница - только если это конец этапа |

Разделы и правила ниже относятся к отчёту-странице. Короткий итог в консоли следует тем же принципам честности (не сделал - так и пиши, «готово» только при зелёном verify), но без структуры.

## Формат

```
## Итог
<одна строка: готово / частично / заблокировано + главное>

## Получилось
- <что сделано> - <пруф: файл, команда, коммит>

## Не получилось / не сделано
- <что> - <почему> - <что нужно, чтобы доделать>
(если всё сделано - "Всё из запроса выполнено", раздел не опускать)

## Проверка
<цифры из Logs\verify\summary.txt: compile / editmode / playmode, RESULT>

## Изменения
- Файлы: <ключевые новые/изменённые, путями>
- Пакеты: <что добавлено/изменено, версии> (если были)
- Git: <коммит hash, запушено или нет>

## Нужно от тебя
- <решение / действие с вопросом, на который можно ответить одним словом>
(нет - "Ничего")

## Дальше
<1-3 пункта, первый - рекомендуемый следующий шаг>
```

## Сохранение и вывод

1. **Файл:** `Reports/YYYY-MM-DD_HHMM_<краткое-имя>.html` в корне проекта. Папка `Reports/` в `.gitignore` - отчёты локальные, в репозиторий не идут.
2. **Шаблон:** копируй `.claude/skills/work-report/template.html`, заполняй блоки (в шаблоне они помечены комментариями), CSS не меняй - все отчёты выглядят одинаково. Разделы те же, что в формате выше. Статус итога - один из `status--done` / `status--partial` / `status--blocked`; строки проверки - `row--ok` / `row--fail`.
3. **Публикация:** инструментом Artifact (publish) - каждый отчёт отдельной страницей: `file_path` = файл отчёта, `icon: "report"`, `description` = строка итога. Ссылку - пользователю.
4. **В чате** - коротко, без дублирования всей страницы: строка итога, цифры проверки, пункты «Нужно от тебя» и ссылка на страницу. Пользователь должен понять главное, не открывая ссылку.
5. Если Artifact недоступен - весь отчёт в чате в формате выше, файл всё равно сохранить.

## Правила

- **Честность важнее красоты.** Не сделал - в «Не получилось». Не проверил - так и пиши «не проверено», а не «должно работать».
- **«Готово» = verify зелёный.** Если verify не запускался или красный, итог не может быть «готово».
- **Каждый пункт «Получилось» с пруфом** - путь к файлу, вывод команды, хеш коммита. Без пруфа это обещание, а не результат.
- **Отклонения от запроса** (сделал иначе, чем просили, или добавил то, о чём не просили) - отдельной строкой в «Получилось» с причиной.
- **Блокеры** (проект открыт в Unity, нет согласия на пакет, нет доступа) - в «Нужно от тебя» с конкретным действием.
- Коротко: весь отчёт помещается на экран. Детали - ссылкой на файл (`Logs\verify\summary.txt`, лог), а не простынёй.
- Язык - русский, без внутреннего жаргона агентов; термины проекта (asmdef, NGO, Relay) - можно.
- Отчёт по шагам (если пользователь просил «отчитывайся после каждого шага») - короткие строки в консоли по ходу работы; страница по этому формату - только если работа закрывает этап GDD или пользователь попросил отчёт.
